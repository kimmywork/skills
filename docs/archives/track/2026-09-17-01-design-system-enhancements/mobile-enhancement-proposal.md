# Design System Skill — Mobile Enhancement Proposal

**状态**: 待 review · **日期**: 2026-09-17 · **说明**: 基于 ClearSight（移动 App）Rebuild 全流程（spec → showcase → 校验 → 两轮打磨）的问题复盘，评估是否增强 `design-system` skill，并沉淀移动端通用规则。

---

## 1. 背景

本次用 `design-system` skill 对一款移动 App（ClearSight，Flutter→KMP 重写，Compose）执行 Rebuild：产出 `DESIGN-SYSTEM.md` + `DESIGN-SYSTEM.showcase.html` + 漂移校验脚本，并经过「SVG 显示修复 → 节/导航/整页场景/响应式修复 → 手机框架高度统一」两轮用户反馈打磨。

以下问题中，**通用文档/Web 场景不会触发**的问题，恰恰是移动 App showcase 特有的；把它们归纳出来，判断是否值得写回 skill。

---

## 2. 遇到的问题与根因

| # | 问题 | 根因 | 已采用的解法 | 教训 / 应沉淀的规则 |
|---|------|------|--------------|---------------------|
| 1 | 内联 SVG 图标塌缩为 0px 或爆炸成 470–610px | 图标串无 `width/height` 属性；仅部分用法有对应 CSS 尺寸；浏览器对无尺寸 `<svg>` 走默认/自动尺寸 | 图标串统一带 `width="24" height="24"`；使用处用 CSS 覆盖到系统刻度（20/24/32/36/64） | Showcase 的图标必须以「显式默认尺寸 + 按上下文覆盖」为机制，禁止裸 `<svg>` |
| 2 | 「文案」「布局」两节完全缺失 | 字符串拼装时残留 `display:none` hack；正则 `.replace(/<section…/,'')` 不可见地改坏了结构 | 重构为 `section(id,title,body)` 统一生成器，禁止在字符串层做结构删除 | Showcase 生成器必须结构化组合，禁止 display:none 占位与字符串正则剥皮 |
| 3 | 侧栏导航锚点大部分失效 | 上一项的 `replace` 剥掉了 `<section id>`，但 TOC 链接列表是独立维护的 → 两侧漂移 | TOC 锚点与渲染节 id 逐一核对，全部命中 | TOC 不能是独立清单，应从「实际渲染出的节」生成（单一来源） |
| 4 | 只有组件样品，没有整页展示 | 产出规范只要求「每个组件的 live sample」，未要求整页场景 | 新增 6 个手机整页 mockup（首页/提醒/播放器/报告/引导/我的） | **App 类系统必须有整页场景**：组件样品证明「零件」，整页证明「系统在真实屏幕上的组织」 |
| 5 | 组件样品用固定宽度（字段 260 / 播放器 380 / 弹窗 320） | 桌面思维——桌面能容纳固定宽度 | 改为 `width:100% + max-width`，样品网格 `repeat(auto-fit, minmax(min(100%,300px),1fr))` | 移动 showcase 一切宽度都要能收缩到手机宽度；整页类用手机宽度（360） |
| 6 | 中窄视口横向溢出 80px | grid 子项 `min-width:auto` 不收缩（内容 min-content 撑宽）；6 列对比度表超出内容列 | 网格项 `min-width:0`；宽表格包进 `.twrap{ overflow-x:auto }`（表内滚动，页面不溢出） | 宽数据表（对比度矩阵）必须内部滚动；网格布局要显式 `min-width:0` |
| 7 | 空态样品「盒子套盒子」显得奇怪 | 把「列表内 120dp 占位」与「整页空态」画成同一种形态 | 拆成两个变体：内联图表占位 + 整页空态（图标+文案+说明+动作） | 空/加载/错误必须按出现的位置分形态展示，不能一张图带过 |
| 8 | 呼吸圆用 `color-mix()` 部分浏览器不显示 | `color-mix()` 是较新 CSS 函数；且展示不应依赖「是否支持某函数」 | JS 从 primary token 计算 `--primary-soft`（rgba） | 派生前景色（alpha/叠加）应在 JS 里由 token 计算，不依赖易变 CSS 函数 |
| 9 | 手机框架高度参差（只有首页高） | `.phone{height:auto}` 内容撑高 → 短页面矮 | `.phone{height:760px}` flex 列；内容区 `flex:1 + overflow-y:auto`；播放器垂直居中填充 | 整页 mockup 必须统一到真实手机高度，内容长则内部滚动、短则居中/留白填充 |
| 10 | 独立维护 spec 与 showcase 的 token → 漂移 | 手写 JSON 被截断、两处各写一遍 | Token Registry 单一来源 JSON；双方各自读取，验证脚本 deep compare 并重算对比度 | 两产物必须「同源生成」，漂移校验是必交付物（已在 skill 中，保留并强化） |

## 3. 需要增强的方面

1. **整页场景是硬要求，不是可选项**。skill 目前要求「live samples of every component」，但缺少「整页/真实叙事场景」。对本类（App）产品，会系统性漏掉：组件如何共处一个屏幕、真实手机高度下的节奏、弹层如何叠加在页面上。
2. **TOC / 锚点 / 节结构的一致性**。showcase 若用 JS 动态生成节，应「先渲染再收集 id 生成 TOC」，杜绝两处手写清单。
3. **移动宽度自洽**。整套展示应能在手机宽度下无横向滚动地观看；样品与整页使用不同宽度策略（样品收缩、整页固定 360）。
4. **图标展示机制**。`<svg>` 需要显式尺寸机制；可将「尺寸刻度 + 上下文覆盖」纳入 showcase 验证项。
5. **模式 × 方案的渲染验证**。移动 App 深色模式是功能，整页场景必须验证两种模式下都成立（本次只验证了对比度，尚未逐场景截图核对暗色布局）。
6. **定位「哪些问题是移动特有的」**：整页高度、底栏固定、弹层叠加、状态栏/安全区、底部触达区、手指热区、people-scaling（动态字体）、空态/加载对整屏布局的影响。

## 4. 移动 App Showcase 特殊展示考虑（建议作为 skill 的「Mobile App Showcase」小节）

### 4.1 框架与画幅
- 强调 **整页场景优先**：一组手机框架（建议 360×760，接近主流竖屏）跑真实用例叙事。
- **统一高度** `phone{height:760px}`，flex 列：状态栏 / 顶栏 / 内容区(`flex:1` 内部滚动) / 底栏(`flex:none`)。内容超出内部滚动，底栏保持固定（还原真实行为）。
- 沉浸型全屏页（播放器）在内容区 `justify-content:center` 垂直居中，不用滚动。
- 弹层/对话框/底表以**叠加层**方式盖在整页上（scrim + 绝对定位），而不是独立样品盒——只有这样才能证明「打断」的真实冲击力。
- 状态栏与安全区用简单条表示；底部导航(底栏)只有在整页里才成立。

### 4.2 图标与资源
- 图标串显式 `width/height`；展示统一提供「系统图标尺寸刻度」（16/20/24/32/36/48/64…）并按上下文覆盖。
- 派生活色（alpha/透明度梯度）由 JS 从基础 token 计算，禁止依赖 `color-mix()` 等易变函数。
- 不引入外部字体/图片/CSS 库；全部 inline，保证零构建、离线可开。

### 4.3 响应式
- 样品网格：`repeat(auto-fit, minmax(min(100%,300px),1fr))`；整页：`minmax(min(100%,360px),1fr)`。
- 固定宽度组件一律 `width:100% + max-width`。
- 网格容器 `min-width:0`；宽数据表（对比度矩阵）用内部滚动 `.twrap`。
- 侧栏 TOC 在窄屏转为水平可折叠条（`<860px`）。

### 4.4 验证（移动特有，评分项）
- SVG 尺寸探针：遍历 `svg.getBoundingClientRect()`，断言落在尺寸刻度范围内、无 0、无爆炸。
- 视口溢出探针：在 ≥2 个宽度档位断言 `scrollWidth ≤ innerWidth`。
- 框架高度探针：所有整页框高度一致。
- 双模式渲染：每个整页场景至少在明/暗各渲一次并人工/截图核对（不只查 token，要看布局是否成立）。
- `prefers-reduced-motion`：确认动效（如呼吸圆）在此媒体下静止。

### 4.5 状态表达
- 空/加载/错误按「出现环境」分形态：内联占位（图表区 120dp 文字占位）vs 整页空态（图标+文案+说明+动作）；两者都要有。

## 5. 移动 App 特殊设计原则（与现有 skill 的关系）

现有 skill 的原则抽取方法（把通用框架推导成产品自己的语言）已经通用；本次暴露的是**移动 App 这类产品需要额外推导的输入面**，建议在 skill 里增加「该类产品的推导提示」：

1. **深色模式 = 功能，不是主题**。夜间是主力使用时段（眼睛已疲劳），深浅两套必须各自独立测量对比，禁止「反相」；整页验证两模式。
2. **扫读优先 / 注意力预算**。首页第一屏只回答「我现在怎么样」；状态必须三联码（颜色+图标+文字）；数据面必须自解释空/载/错/有。
3. **每面一主操作**；打扰（系统主动打断）只允许与产品核心价值相关且必须可逆。
4. **数据跳变、绝不渐变动画**：健康状态/计时等是离散数据，渐变会暗示过程；动效预算只给「引导动作」（呼吸圆）。
5. **触达与热区**：触点 ≥48×48；主操作放拇指可达区；底栏是移动特有的一致导航位。
6. **动态字体**：支持系统字体缩放到 2.0x 且不截断——移动 OS 的字体缩放和桌面判定标准不同。
7. **安全区 / 边缘到边缘**：状态栏、手势条、刘海要进展示与规范。
8. **外部内容边界**：医疗免责、法律条款等其余方所有内容不得被静默重样式（移动健康类产品极常见）。
9. **效率路径**（移动特有增强）：快捷入口（主按钮直达）、高频操作一步化。

> 判断：principle#1/2/3/5/6/7/8 都应写回 skill 作为「推导时必问的面」；#4/#9 更多是产品特定，保留在「样例」级别即可。

## 6. 对 `design-system` skill 的增强建议（候选清单）

按「是否值得增强、工作量、优先级」列出。`N` = new，`R` = 改现有。

| # | 建议 | 类型 | 优先级 | 工作量 |
|---|------|------|--------|--------|
| 1 | Showcase 要求增加「整页/场景叙事」：App 类产品必须提供一组真实屏幕 mockup（统一手机框架 + 弹层叠加 + 沉浸页） | N | 高 | 中 |
| 2 | Showcase 结构约束：节必须由生成器产出稳定 id；TOC 从渲染结果生成；禁止 `display:none` 占位与字符串正则改结构 | R | 高 | 低 |
| 3 | 移动响应式约束：样品可收缩到手机宽、整页固定手机宽；网格 `min-width:0`；宽表内部滚动 | R | 高 | 低 |
| 4 | 图标展示机制：内联 `<svg>` 显式尺寸 + 系统尺寸刻度 + 上下文覆盖 | N | 高 | 低 |
| 5 | 派生前景色（alpha）由 token 计算，不依赖 `color-mix()` 等不稳定函数 | N | 中 | 低 |
| 6 | 移动展示验证清单（probe）：SVG 尺寸、多档视口无溢出、框架高度一致、明/暗双模式渲染核对、reduced-motion 静止 | N | 高 | 中 |
| 7 | 空/加载/错误按出现环境分形态展示（内联 vs 整页两种变体都要） | R | 中 | 低 |
| 8 | 无独立两产物漂移：强调 Token Registry 单一来源 + 自动校验（现状已有，强化为「必须由同一份数据生成」） | R | 中 | 低 |
| 9 | 移动 App 推导提示面（§5 的 1–9 条）并入「建立基座」步骤的输入检查 | R | 高 | 低 |
| 10 | 深色模式整页验证进入非 negotiable（对 App 类产品） | R | 高 | 低 |

### 6.1 建议的实施方式
- `resources/checklist.md` 的 Showcase/验证部分增加「移动 App 展示检查」一节（上面 #2–#7 的可执行版本）。
- 在 skill 主文档「Output → Showcase」小节增加「场景叙事」「结构约束」「移动响应式」「图标机制」四条要求与反例（`display:none` hack、裸 svg、无整页）。
- 如果移动是主要目标，可在 skill 开头按产品类型（文档型 / 网站型 / App 型）给出口径差异，App 型默认启用「整页场景 + 双模式验证」。

## 7. 结论

**有必要增强，且增强成本低、收益集中在展示可信度与移动正确性上。** 核心取舍是：

- 必须加：#1 整页场景、#2 结构/TOC 约束、#3 移动响应式、#6 移动验证清单、#9 推导输入面。
- 建议加：#4 图标机制、#5 派生色、#7 状态分形态、#10 双模式硬要求。
- 不必加（保持通用）：把具体文案（如 ClearSight 的「立即放松」）写进 skill、引入单一产品专用规则；这些应留在产品规范里。

> 一句话：skill 目前把「组件 = 展示的全部」当作默认，这对文档/网站成立，对 **App 是残缺的**——组件必须回到真实屏幕与真实叙事里才有意义。补齐「整页场景 + 移动响应式 + 移动验证」三块后，移动 App 场景的产出会显著更可信。
